### Get the ROM image

**[Download](../../download.md) from release**

If you're using a release ROM, please ensure that you've inserted extra firmware
required refer to the [guide](../install/ivy_has_common.md) for that (, failure
to adhere to this advice will result in a bricked machine):

- Intel ME (vendor blob)


**[Build](../build/) from source**

	./mk -b coreboot topton_x2e_n150


### Internal/Software Flashing

**WARNING: DO NOT internal-flash on first install. Updates between Libreboot
versions is fine, but the vendor firmware seems to set PRx registers blocking
flashes to 0x600000-0x65ffff (384 KiB area) and AMI NVRAM is still intact.
IFD FLMSTRs are all 0xffffffff so this is likely PRx (protected range)
registers being set by the factory firmware. THEREFORE: external flashing
recommended, on initial Libreboot installation. The `fallback/postcar` part
in CBFS happened to be in that location under testing, so internal flashing
on initial installation will likely lead to a brick.**

**Default Libreboot firmwares [updatable](../install/simplified-sw-flashing.md).**


### External/Hardware Flashing

**This** method is recommended, for the initial installation when switching
away from the original factory firmware.

**Backup and flash according to the [guide](../install/simplified-hw-flashing.md).**


The board has a single 16 MiB SOIC-8 flash chip on the bottom side
of the motherboard. To access it, you need to disassemble the case
and remove the board, using a Phillips head screwdriver.

The BIOS flash chip is in the bottom left of the photo below. It is
silkscreened with text "SPI_ROM". Do not mix it up with the 4 other
similar flash chips marked LANx_ROM, those are for the Ethernet NICs.

### Untested/not working

- 5G modem slot untested

- USB 3.0 ports, only work at up to 2.0 speeds (480Mbps)

#### FreeBSD UART issue (plus fix)

UART at 0x3f8: TX does not complete unless RX activity occurs. Coreboot's
own output works fine, but FreeBSD using uart0 at 0x3f8 as console will stall
randomly during boot and only progress while characters are received at the
serial port. Perhaps a patch could be put somewhere to keep the line hot to
mitigate this?

It will eventually kernel panic, thus:

```
panic: spin lock held too long
_mtx_lock_indefinite_check() / _mtx_lock_spin_cookie()
uart_cnputc() / cnputc() / cnputsn() / putchar() / kvprintf() / printf()
tc_init() / tsc_calibrate() / cpu_initclocks()
```

FreeBSD also prints `uart: ns8250: UART FCR is broken (0x1)` - LSR.THRE is not
set (or set late) unless there is RX activity.

Recommended workaround: `hint.uart.0.disabled="1"`

This is based on the following bug report: <https://codeberg.org/libreboot/lbmk/issues/457> - which
states also that input is extremely slow on SeaBIOS and GRUB, but please note
that this was the bare-metal SeaBIOS/GRUB payloads - modern Libreboot ships
with EDK2 instead, and GRUB/SeaBIOS are provided as EFI builds. EDK2 and
EFI GRUB/SeaBIOS will need to be re-tested.

Nothing was done for Libreboot 26.10 to remedy this, as this workaround
should do nicely; no issues were yet reported on other operating systems.

#### FreeBSD SCI storm bug

MADT: `INT_SRC_OVR (bus 0 bus_irq 9 global_irq 9 high level).`

On FreeBSD `irq9: acpi0` fires ~130,000-180,000 times/s. DTrace shows
AcpiEvSciXruptHandler -> AcpiEvGpeDetect / AcpiEvFixedEventDetect with no GPE
and no fixed event ever dispatched. On Linux (Mint 22 live, same firmware)
`/sys/firmware/acpi/interrupts/sci` stays at 0.

Recommended workaround: `hw.acpi.sci.trigger="edge"`

This does not affect Linux.

Reported here: <https://codeberg.org/libreboot/lbmk/issues/457>

#### Possible NVMe SSD issues.

A user reported that their Intel SSDPEKKF256G8L SSD did not work in the M2
slot (`pcie_rp9`, 00:1d.0). Not detected. Linux dmesg:

```
pci 0000:00:1d.0: broken device, retraining non-functional downstream link at 2.5GT/s
```

A different NVMe SSD (LENSE30256GMSP34MEAT3TA) worked in the same slot, and
the Intel one did work in factory firmware. Beware possible issues with SSDs.

Reported here: <https://codeberg.org/libreboot/lbmk/issues/457>

Nothing for this was done on Libreboot 26.10, but perhaps disabling hotplug
in FSP might mitigate it; we had issues with SSDs on some other boards as
well, specifically Kabylake desktops.

#### More FreeBSD errata

FreeBSD users should set `vm.pmap.pcid_enabled="0"` on this board, as per
Alder Lake-N PCID erratum.

Reported here: <https://codeberg.org/libreboot/lbmk/issues/457>

The same person also measured that the logic level on their UART was 9.5V,
shunted between TX and RX. This is equivalent to RS-232 logic levels.
